# SEC-IMPL-1 / TEST-TRUTH-1: security participation and test integrity

Status: user-approved operating supplement, 2026-11-13. Actual review quality/runtime NOT_MEASURED.
This is not a quotation from Nishiguchi or Numata. Higher-priority project/platform rules and explicit access limits remain in force.

## SEC-IMPL-1: every implementation needs a security pass

- Applies to every authorized task that implements or changes application code, test code, dependencies or runtime configuration. Pure documentation/planning without implementation is exempt. Small/UI-only changes are not silently exempt.
- PL extracts ticket-visible identity, authorization, PII, inputs, state updates, public API, dependency and DB/async risks as acceptance constraints. An empty ticket risk list is not security clearance.
- HQ reassesses the actual changed-file inventory, contract and affected source after the first meaningful implementation diff, and again after relevant edits. Invoke a real read-only sec-arch owner as soon as a reviewable snapshot exists; never leave a specialist idly waiting for code changes.
- When Codex implements, prefer a fresh, permitted Claude Code sec-arch owner independent of implementer/PCR conclusions. Never route it through a QA/E2E-only transport. Codex-only sec-arch is same-family evidence, not cross-model approval. If the selected workflow requires independent Claude security confirmation and the tools/permission are unavailable, record SEC_PENDING and do not claim release approval.
- The security owner assesses reached authentication/authorization and IDOR/owner/tenant boundaries, untrusted inputs, secrets/PII/logs, injection/XSS, applicable CSRF/CORS, public/intra-service API exposure, dependency/configuration changes and security effects of updates/rollback. For unaffected areas record reasoned NOT_APPLICABLE; no exhaustive untriggered audit or speculative defects.
- Use actual owner ID, snapshot, relevant original rules, checked source, findings and pending evidence in the existing record. Return SEC_CLEAR only when all assigned security obligations are checked on that snapshot without open findings or material gaps; else SEC_FINDINGS/SEC_PENDING. This is a scoped security result, not general ADV/QA approval.
- The implementation owner fixes findings and the original security owner rechecks fixes and affected changes. Before final QA/review, obtain current-snapshot SEC_CLEAR or the same owner's explicit delta/impact confirmation. Never carry stale approval over changed code, tests, rules or configuration.
- In explicitly selected pcr-development only, actual changes to API producer/consumer contracts, permission/actor design, concurrent writes/transactions, persistence/migrations, retries/async durability, multi-screen state contracts or backwards compatibility trigger independent Claude Code adviser (ADV). Record ADV_REQUIRED with reached boundary/evidence, or ADV_NOT_APPLICABLE with inspected reasoning. An empty PL risk list never excuses HQ's diff check. Triggering the adviser does not grant extra execution/edit permissions or automatically activate other review layers.

## TEST-TRUTH-1: preserve bug-detecting assertions

- Derive test expectations from requirements, agreed observable behavior and real producer/consumer contracts, not from the newly changed implementation. Green CI, zero failures, or coverage percentage alone does not establish correctness.
- Do not obtain passing tests by deleting/skipping/isolating cases with .only/.todo, relaxing assertions, rewriting snapshots to reflect a bug, overmocking, altering fixtures to bypass a failing path, swallowing errors, lowering thresholds, disabling checks, or excluding affected files/configuration.
- A genuine requirement change or proven incorrect existing test can justify a test correction. For each removed/weakened/changed assertion, snapshot, mock/fixture or runner constraint, record original protected behavior, authoritative updated expectation, retained equivalent or stronger guarantee, and targeted verification (or NOT_RUN). To remove redundant cases, name the surviving assertion proving the same distinct guarantee.
- When a test fails, inspect implementation and authoritative contract first. Do not fix only the expected value without proving why the old value was wrong. Preserve discriminating happy/fail cases, especially authorization denial, invalid input, retry/rollback, duplicates and concurrent updates.
- QA/E2E independently inspect changed assertions, snapshots, skips, filters, mocks, fixtures and test config. Ask whether retained assertions would reject the original regression. Actual mutation/before-after execution is evidence only when already authorized and performed; otherwise label NOT_RUN.
- Unsupported weakening is a tracked finding; missing mandatory evidence is PENDING/REQUEST_CHANGES under the active review verdict. The security owner and QA/E2E reviewers remain read-only unless a separate explicit task permits otherwise. Never start CI, expand permissions or claim execution from source inspection.
- Record exact source revision, selected cases/commands/exit, remaining gaps and each owner's delta confirmation once. Reuse unchanged evidence; do not create another reporting document per review.
