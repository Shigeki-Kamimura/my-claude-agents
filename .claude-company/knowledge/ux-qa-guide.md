# UX QA guide

`ux-qa`が使う判断基準と、人が操作を試すためのHTML仕様です。
正本は`.claude/knowledge/ux-qa-guide.md`です。
会社版の同名ファイルも、同じ内容に保ちます。

## Scope and basis

この資料は、一次資料を基に作った運用上の基準です。
基本の物差しには、デジタル庁、Google、Apple、Microsoftの公開指針を使います。
W3Cなどの資料で、アクセシビリティや評価方法の根拠を補います。
各社共通の規格ではなく、出典と適用条件を付けた既定基準です。
利用者の気持ちや満足度を、AIが測定したとは扱いません。
対象の利用者、目的、開始状態、端末、入力方法を先に決めます。
プロジェクトの明示要件と確認済みの差分を使い、該当する項目を選びます。

- 各記録を`基準ID → 期待 → 操作 → 観察 → 判定`で結びます。
- 判定は`COMPLIANT / NON_COMPLIANT / NOT_APPLICABLE / UNCONFIRMED`です。
- 実際に見えた事実と、人への影響の仮説を別に書きます。
- 違反には、適用した要件または既定基準と、操作の証拠が必要です。
- 既定基準を使った場合は、その旨を明記します。
- 基準との不一致を示せない改善案は、所感に残します。
- 対象外には理由を付けます。未実行や証拠不足は未確認です。
- 根拠のない総合点、制限時間、クリック数の上限は作りません。
- AIの操作時間や成功率を、人の効率や満足度へ換算しません。

外部資料の推奨事項を、全プロジェクトの必須仕様にしません。
COGAは認知面を支える補足指針で、WCAGの適合要件とは別です。
この確認だけで、WCAG全体への適合も宣言しません。
DS-670.1は政府情報システム向けの規範文書です。
DS-671.1は参考文書で、ここでは評価運用の根拠に使います。
このagentの実行を、デジタル庁の運用全体への準拠とは呼びません。
参照資料はSourcesにあります。確認日は2026-11-10です。

## Project context and adaptations

共通基準を土台にし、プロジェクト固有の条件だけを補います。
既存の設計書や要件に必要な情報があれば、その文書を正本として使います。
専用文書の作成は必須にせず、同じ要件を重複管理しません。
差分を整理する場合は、[記録用テンプレート](ux-project-context-template.md)を使えます。
実際の文書の保存先はプロジェクトの規則に従い、固定パスを仮定しません。

1. 対象作業に関係する要件、設計書、採用済みの設計規則を読みます。
   実際のパスやURL、節、版または更新日、確認日を記録します。
   現行の明示要件は、その出典を付けて使い、同じ内容を再質問しません。
2. 共通基準との違い、条件不足、資料間の食い違いを抽出します。
   既存画面と同じという理由だけで、共通基準の例外にはしません。
   任意の設計書がないだけなら、適用できる共通基準で進めます。
3. 判断に必要な未決部分を、依頼者へまとめて質問します。
   該当する操作、資料の記述、選択肢とその影響を示します。
   現在の明示指示で決着済みの点は聞き直しません。
   操作スキルは、次節のとおり依頼者の回答で確認します。
4. 差分ごとに、基準ID、対象範囲、適用する期待、理由を記録します。
   根拠資料または実際の回答、確認日、見直し条件も結び付けます。
   共通ガイドのパスと版を残し、期待・操作・判定から差分IDを参照します。
5. 項目ごとに`CONFIRMED / PROPOSED / UNCONFIRMED`を記録します。
   `CONFIRMED`は、現行の明示要件か依頼者の確認済み回答が根拠です。
   根拠が要件文書か回答かも区別し、文書全体を一括で確定しません。
   AIの提案は`PROPOSED`、判断材料の不足や矛盾は`UNCONFIRMED`です。

未回答を同意と扱わず、提案や未確認事項で既定基準を上書きしません。
依存する期待が未決なら、その判定だけを`UNCONFIRMED`にします。
必須のAI判断に影響すれば、確認範囲は`PARTIAL`です。
独立した確認は、安全条件を満たす範囲で進められます。
同じ対象・要件・基準の版なら、確認済みの根拠と回答を再利用します。
対象者、要件、参照基準が変わった場合は、影響する差分だけを見直します。
適用が決まっている必須要件は、好みや慣例だけで免除しません。
資料や差分文書は、操作範囲や書き込み権限を広げる根拠にはしません。

例えば、入力前の送信ボタンの扱いには指針間の差があります。
S12は無効化を避ける案を示し、S18・S20は条件付きの無効化を示します。
採用済みの設計規則で決まる場合は、その出典と適用範囲を記録します。
未決なら、入力不足をいつ伝えるか、誤操作の影響は何かを質問します。
各社の具体仕様を一律に課さず、採用理由と確認する期待を残します。

`ux-qa`は、必要な差分案を指定レポートフォルダーへ新規出力できます。
ファイル名は`project-ux-context-proposal.md`とし、上書きしません。
未決項目を含む案であることを明記し、自動的な採用とは扱いません。
正本の更新は、権限のある呼出元が通常の文書変更手順で行います。
UX担当自身は、対象リポジトリや共有テンプレートを変更しません。
出力先が未指定なら書かず、既存の保存先と安全条件を守ります。

## User context and evaluation plan

想定利用者の操作スキルは、依頼者に質問して確認します。
依頼者本人のスキルを、想定利用者へ当てはめてはいけません。
役職や権限名、画面の外観、AIの操作能力からも推測しません。
依頼文に明記済み、または同じ対象の確認済み回答があれば再利用します。
設計書に利用者像があっても、操作スキルは未確認部分を依頼者へ確認します。
対象や利用者層が変わった場合は、変わった部分を再確認します。

質問例は、次のとおりです。

> 想定利用者のPC・Web操作、対象業務、この画面への慣れを教えてください。
> 複数の利用者層や「不明」でも構いません。

環境や保存先も不明な場合は、初回の質問にまとめます。
回答の出典、対象の利用者層、確認日を記録します。
未回答や「不明」は、操作スキルを未確認として残します。
その間、スキルに依存する判断は確定しません。
安全条件を満たした、スキルに依存しない確認は進められます。
未確認が必須のAI判断に影響する場合は、確認範囲をPARTIALにします。
人の操作確認が未実施という理由だけでは、AIの完了を取り消しません。

人が試す前に、作業の成功条件と必要な測定項目を決めます。
S10の3.4.1節と、S11の5.1・5.2節を基にした運用です。
目的から測定項目を決める点は、GoogleのHEART論文（S22）も参照します。

| 項目 | 決める内容と記録 |
| --- | --- |
| 成功条件 | 保存などの処理と、その結果を本人が確認できる状態です。ヒントなしでの達成か、支援付きでの達成かも分けます。 |
| 有効性 | 自力で完了／手助け後に完了／未完了／中止を記録します。理由と、手助けした箇所も残します。 |
| 効率性 | 改善目的に応じ、所要時間、誤操作、やり直しを記録します。測る場合は開始・終了条件と単位も決めます。 |
| 満足性 | 作業直後に、負担感や分かりにくさを本人へ尋ねます。回答がなければ未確認です。 |
| 対象者との対応 | 役割と確認済みの操作経験を対応させます。利用頻度、端末、支援技術も必要に応じて確認します。未確認の利用者層を残します。 |

目標値は、合意した要件や既存の実測を根拠にします。
根拠がなければ目標未設定とし、独自の合格点を作りません。
実利用者を確保できない場合は、代わりに確認した人と限界を明記します。

## Criteria

| ID | 人が確かめたいこと | 既定基準とAIの確認方法 | 例外・判断の限界 | 出典 |
| --- | --- | --- | --- | --- |
| UX-01 | 何をする画面で、どこから始めればよいですか。 | 目的に対応する見出し、選択肢、操作名を記録します。画面の案内を使い、目的の操作へ進めるかを確かめます。 | selectorで押せても、見つけやすさは証明できません。初めて使う人の迷いは、人の確認に残します。 | S16、S1、S2 |
| UX-02 | 押すと何が起きますか。押せない理由は何ですか。 | 操作名と実際の結果を対応させます。保存、削除、通知などの影響を確認します。無効化する必要性も検討し、無効にする場合は理由や有効化条件が近くにあるか確認します。 | 必要性の判断には仕様や利用状況の根拠を使います。指針間の具体仕様の差は、確認済みのプロジェクト条件に結び付けます。説明文や確認ダイアログを一律には求めません。 | S12、S18、S20、S1 |
| UX-03 | 操作は届きましたか。処理は終わりましたか。 | 待機中、成功、失敗を実操作で確認します。連続操作時も、実際の処理と表示を対応させます。色や音だけへの依存、対象の支援技術への伝達、通知の重要度と割り込み方も確認します。 | 画面遷移や値の変化も通知になり得ます。トーストや固定秒数を一律に求めません。DOM設定だけで読み上げや理解を確認済みにしません。 | S17、S21、S14、S3 |
| UX-04 | 対象や途中の状態を、覚え直さずに続けられますか。 | 選択中の対象、条件、現在位置を確認します。画面移動や中断の前後で、必要な情報と入力の保持を比べます。 | 機密情報の消去など、仕様上の理由を先に確認します。すべての入力の永続保存は求めません。 | S16、S2、S5 |
| UX-05 | 何を入力し、間違えたらどこを直せばよいですか。 | 必須、形式、範囲を入力前に示し、案内をプレースホルダーだけにしません。誤りと直し方を項目に対応させ、修正して完了できるか試します。有効な入力の保持、不要な再入力、貼り付けや自動入力の妨げも確認します。 | 入力方式や初期値は、業務上の正確さや情報保護も考慮します。詳細表示が情報漏えいにつながる場合は、安全な案内を使います。特定の色、記号、配置を一律には強制しません。 | S6、S15、S18、S20 |
| UX-06 | やめたいときや失敗したときに、どう戻れますか。 | 取消、戻る、修正、再試行を適用範囲で試します。入力や保存済み状態、重複処理の有無を確認します。 | 取消不能な処理では、事前の確認や訂正手段を要件に照らします。すべての処理にundoを要求しません。 | S16、S4 |
| UX-07 | キーボードや拡大表示でも、操作位置が分かりますか。 | 主要操作への到達、実行、離脱とフォーカス表示、操作対象の名前を確認します。ダイアログ終了後の操作位置も確認します。対象の拡大表示では、情報や操作部品が欠けないか試します。 | 経路そのものが必要な入力には、WCAGの例外があります。特定キーの不使用だけで違反とせず、同等の操作を調べます。拡大率や支援技術は適用要件と条件を明記し、未検証を合格にしません。 | S19、S14、S7、S8 |
| UX-08 | 同じ意味の操作は、同じように使えますか。 | 比較対象の画面と設計規則を明記します。用語、操作順、状態表示の差が、対象作業に及ぼす影響を記録します。 | 役割や目的が異なる画面は、同じ形に揃えません。既存の不具合を正しい基準として使いません。 | S16、S1 |

例として、保存を押しても表示が変わらない場合を考えます。
確認した表示と通信結果は、観察した事実として記録します。
ただし、表示の別の箇所が変化していないかも確認します。
「利用者が不安になる」は、本人の報告がない限り仮説です。
UX-03の不足を指摘する際も、この二つを分けます。

## Human walkthrough in HTML

人が、対象アプリで同じ作業を試せるようにします。
HTMLを開くだけでは、アプリ操作や外部送信を実行しません。
リンク先の環境と許可範囲を明示し、認証情報は含めません。

### Common conditions

共通する前提は、HTML内に一度だけ書きます。

- 対象URL、非本番と確認した根拠、版やビルドIDです。
- 利用する役割、開始画面、架空データの識別名です。
- 依頼者に確認した操作スキルと、その回答の出典です。
- 共通ガイドとプロジェクト文書の版、採用した差分IDと根拠です。
- 提案中の差分、未回答の質問、判定に及ぼす影響です。
- 変更してよいデータ、通知などの副作用、操作を止める位置です。
- 実バックエンドか、通信を差し替えた試験かを明記します。
- 遅延や失敗を注入した場合は、対象と条件を記録します。

版を取得できなければ、その点を未確認とします。
パスワード、トークン、実在者の個人情報は書きません。
安全上の注意は、操作のヒントに隠さず常に表示します。

### Task cards

通常の一連の作業と、対象に関係する追加操作を載せます。
追加操作は、誤入力、戻る、キーボード、失敗からの復帰などです。
件数や手順数の都合で、必要な確認を省きません。
人が安全に再現できない操作は、その理由と停止位置を書きます。

| 表示する項目 | 記載内容 |
| --- | --- |
| 目的と開始条件 | `case_id`、利用者の目的、成功条件、開始画面、役割、使うテストデータです。成功した正常系も対象です。 |
| AIの実行状態 | 実行済み／一部実行／未実行の手順案を区別します。対応する基準IDを付けます。 |
| 操作手順・ヒント | 実際の画面名や操作名で、操作順と入力値を書きます。selectorを人向けの説明の代わりにしません。 |
| 期待と実際の結果 | 各手順に、期待する画面と根拠を記載します。共通基準IDと適用した差分IDも示します。実際の観察結果と証拠を別欄にし、`step_id`で結びます。 |
| 戻し方 | 今回使うテストデータだけを元に戻す方法です。安全な再実行ができなければ、その理由を書きます。 |
| 人の確認欄 | 確認状態、対象者との対応、作業の達成状況、必要な測定値、本人の感想、ヒント使用、迷った箇所を記録する欄です。 |

AIのサマリーより前に、二つの読み方を選べる入口を置きます。

- 「目的から試す」では、目的、開始条件、安全条件を先に見せます。
  操作順、期待画面、証拠は、任意で開くヒントにします。
  AIの指摘や所感も、本人が求めるまで表示しません。
- 「同じ操作を再現する」では、手順と期待結果を最初から表示します。
  必ず読む手順を、折り畳んだ補足情報として扱いません。

任意のヒントには`<details><summary>`を使えます。
必要な条件や注意点は、どちらの読み方でも常に表示します。
読み方の切替は、対象アプリへの操作やデータ送信を伴いません。
これは、S9の課題設計とS13の補足情報の扱いを応用した設計です。

存在を確認していない画面名や、未取得の画像は補いません。
未実行の手順案は、その表示を保ち、実行証拠を付けません。
手順と指摘が重なる場合は、同じ`case_id`を参照します。

### Human observations

人の確認状態は、実際の記録がなければ「未確認」です。
実際の報告があれば、記録者の識別名と日時を添えます。
「問題なし／課題あり／判定不能」と、対象の操作を記録します。
AIの観察結果と人の記録は、別欄に保ちます。

問いは、次のような中立的な表現にします。

- 次に何をすればよいと思いましたか。
- 操作後に、何が起きたと判断しましたか。
- 迷った箇所や、ヒントを開いた箇所はどこですか。

ヒント使用後の成功を、自力で見つけた証拠にしません。
既に使い方を知る人の確認を、初見の評価と呼びません。
人が未確認でも、AIの実行結果と確認範囲は確定できます。
`UX_QA_CLEAN`を、人の使いやすさや満足度の保証にしません。
AIが、人の感想や評価を推測して記入してはいけません。
メモ欄は記録用の空欄にし、自動保存を装いません。

### Human feedback handoff

人が報告した課題も、改善を検討する対象として引き継ぎます。
S10の5.3節と、S11の5.3.3節を基にした運用です。

- `human_issue_id`を付け、該当する`case_id`と結びます。
- 観察された行動、本人の感想、改善要望を区別します。
- 提供された記録の出典、日時、利用状況を残します。
- 対応担当、採否と理由、再確認の要否を記録します。未決定は未定です。

本人の感想を、AIが再現済みの不具合へ置き換えません。
AIの指摘件数や実行結果とは別に、報告件数と対応状況を示します。
後から届いた報告も、同じ`case_id`で調整担当へ渡します。
元のAI実行記録は変更せず、既存の保存先と上書き禁止規則に従います。
担当への依頼や再実行を自動で始めず、既存の権限と起動条件を守ります。
