# CR並列試行の手順と記録

[標準方針](claude-review-policy.md)と[使用率の試行記録](claude-review-trial.md)に基づく試行です。
この文書は設定リポジトリ内の試行記録です。レビュー担当への読取指定ではありません。
運用上の試行ルールであり、Nishiguchi原則の引用や会社方針ではありません。
標準方針と矛盾する場合は、標準方針とプロジェクトの規則を優先します。

## 位置づけ

- 新しいレビュー層ではありません。明示依頼された `cr:` を並列で試すものです。
- L2（`adv:`）は別モデルで、引き続き独立して実行します。この試行の結果を `adv:` の入力にしません。
- 自動チェーンにしません。Explicit Workflow の外で、自動のレビュー連鎖を追加しません。
- 依頼がない限り、CR以外の層（qa/e2e/adv/rev）は起動しません。
- レビュー依頼だけでは、コード変更やテスト実行を始めません。

## 構成

1. 差分・要件・適用規約を固定します（対象base/head、未コミット範囲、設定の版）。
2. 同じ入力を、次の2体に渡します。

| 担当 | 重点 | 広げない範囲 |
|---|---|---|
| CR-A | コード、状態、型、局所規約、正常系・失敗分岐 | 設計判断（L2の担当） |
| CR-B | 変更に直接関係する仕様・手順・生成物・期待値との一致 | テスト全体の十分性（QA/E2E）、L2の設計判断 |

3. 両CRに共通の必須観点を持たせ、重点だけを分けます。
   必須観点は、適用規約と例外の確認、要件との照合、反証と正常系の確認です。
4. 初回結果を出すまで、CR-AとCR-Bは互いの結果を見ません。
5. 初回結果を、集約・検証担当へ渡します。

## 集約・検証担当の契約

担当するのは次の検査だけです。PR全体を再レビューしません。

- 指摘ごとの妥当性（根拠となるコード・要件の確認）
- 規約の適用条件と例外
- 重要度の判定。次の3点を分けます。
  - 不一致の有無
  - 影響
  - 今回PRでの修正義務
- 指摘の重複
- 両CRが必須観点を実施したかの確認。未実施の検査だけを補います。

守ること:

- 棄却を自動的に正解にしません。棄却には理由を書きます。
- 1体のみの指摘でも、根拠があれば残します。
- 判断が割れたら、争点と不足証拠を記録します。
- 元担当の指摘を、無断で消しません。元の記録は残し、集約側の判定を別に書きます。
- 結果をCONFIRMEDだけに潰しません。「不一致の存在」「今回PRでの扱い」「重要度」を別欄に記録します。
- 新しい指摘は、必須観点の未実施を補った場合に限ります。範囲を広げません。
- コード変更・テスト実行・追加の層の起動は含みません。

## 開始前条件

次の3つを満たすまで、測定として開始しません。

1. 必須観点の実施確認
   各CRが、読んだ規約・節・例外を `Rules loaded` に記録します。
   未読の必須節は、未完了として残します。
2. CR-B範囲の歯止め
   CR-Bの範囲を、変更に直接関係する仕様・手順・生成物・期待値に限ります。
   テスト全体の十分性とL2の設計判断には広げません。
3. 答えを伏せた別PRで測る
   PR #1278の指摘は、担当にも規則にも渡しません。
   実装者の合格判断とモデル名は、レビュー入力から外します。
   期待結果は、担当へ渡す前に別記録へ固定します。

## 評価基準

以下は暫定の目安です。

- 追加検出が、複数のPRで出るか。
- 過剰指摘が、追加検出を上回らないか。
- 最低3PR程度で判断します。1PRで一般化しません。
- 同一モデルで範囲だけ分けた場合と、モデルを変えた場合は、別条件として測ります。
- 自己選好バイアスは、新規セッションだけでは解消済みとしません。
- 指摘数、読取量、短時間、低使用率だけでは合格にしません。
- 品質と使用量は、同じ対象版・同じ入力で比較します。

## 限界

- PR #1278（1件・4指摘）の相互検証は暫定です。独立した正解との照合ではありません。
- 1PRの結果から、並列CRの有効性を結論しません。
- この文書の作成は、並列CR運用の採用を意味しません。
