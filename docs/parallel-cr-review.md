# 並列CRと限定検証の使い方

PCR-1は、明示して使うL1.5の試行ルールです。
通常の`cr:`、モデル設定、QA/E2E/ADVの担当範囲は変えません。
共通原文は`.claude/knowledge/parallel-cr-review.md`です。
company版は同内容を保持します。スキルは原文への入口です。
起動例は下記の通常の依頼文でも使えます。
スキルの自動検出やDesktopへの反映済みは前提にしません。

CodexのPCRには、固定のファイル数上限を設けません。
CR-A・CR-Bは、それぞれ対象差分全体を確認します。
読み取りは分割でき、未確認の範囲があれば承認しません。
通常CR、Claude側CR/ADV、QA/E2Eの枠は維持します。
実装と並行して使う手順は、[PCR開発フロー](pcr-development.md)を参照してください。
単独PCRの依頼から、その全手順は自動開始しません。

## 1. 並列CRを依頼するプロンプト

対象PRを指定した会話で、次を渡します。
PRが特定できない場合は、対象を確定するまで起動しません。

```text
このPRを、PCR-1の並列L1.5試行でレビューしてください。
.claude/knowledge/parallel-cr-review.mdの原文を読んでください。

まずPRのbase/head、三点差分ならmerge-baseも固定してください。
要件と規約の版、対象外、未コミット変更の扱いを記録してください。
ローカルのcode-quality-reviewerを使います。
GitHub Actionsのレビュー結果で代用しないでください。

私が許可するのは、次の3担当による読み取り専用の確認です。
1. 新規CR-A：共通必須観点に加え、変更処理・状態・失敗経路を重点確認します。
2. 新規CR-B：共通必須観点に加え、直接関係する仕様・手順・生成物を重点確認します。
3. 新規検証担当：両結果の確定後、全指摘と必須観点の未確認だけを検証します。

AとBには相手の結果、過去の承認、実装時の判断を見せません。
確認箇所だけでなく、条件・根拠・対象外・不明を記録させてください。
規約の本文、適用条件、例外、注入済み規約の版の一致を確認してください。
不一致の存在、発生時点、PR対象、規約、重要度、閉鎖状態を分けてください。
既存不具合は、同じファイルやセルを変更しただけで今回の必須修正にしません。

変更前後の表示・状態と画面ID・ルートから、関連文書の検索対象を決めます。
変更ファイルだけでなく、直接関係する運用・デモ手順も確認してください。
DOC-IMPACTには検索語・対象範囲・一致箇所の判断を残してください。
ARTIFACT-DELTAには対象ケース・セルと、選定理由を残してください。
Excelは変更セルと必要な関連値を照合し、全件・全列の比較は既定にしません。
全件確認が規約上必要なら、その根拠を記録してください。
QAのテスト網羅性やADVの権限・業務判断まで調査を広げないでください。
検証担当は、重複候補を元ID付きでまとめ、規約と対象範囲から確認してください。

必須の未確認はPARTIAL/BLOCKEDとして残します。
判断が割れた指摘を多数決や独断で消さないでください。
コード・文書の変更、テスト・CI等の実行、QA/E2E/ADVの起動は禁止です。
許可されていないBashや解析手段は追加しないでください。
結果から追加レビューや修正ループを自動起動しないでください。

実際の担当ID・モデル、全体の時間・取得できた利用量も記録してください。
各担当の起動・終了、初回2担当の完了、検証開始・終了を時刻付きで残します。
壁時計の経過時間と、並列担当の作業時間の合計を区別してください。
list_agentsや短い間隔の確認は使わず、起動・完了イベントで記録します。
取得できない利用量はNOT_MEASUREDとしてください。
最後に各担当の判定と、集約担当の未解決事項を分けて報告してください。
```

### 判定の食い違いまで1回だけ整理する場合

上の依頼文に、次を追加します。追加しなければ3担当で終了します。
新規担当の追加や、PR全体の再レビューは許可しません。

```text
reconcile_once: true
検証後、棄却・対象範囲・必須確認に争点が残った場合に限り、
原担当ごとにまとめて1回だけ応答を求めることを許可します。
元の担当を再開し、そのIDと提示された証拠だけを確認させてください。
規約や権限が再開を許さない場合は、代替起動せず未解決で終了します。
親は原担当の判定を上書きせず、変更前後の判定と根拠を残してください。
応答の内容から追加ラウンドを始めないでください。
```

## 2. PR #1278の未完了確認を補うプロンプト

これは新規発見試験ではありません。F-03/F-04の事実確認を再利用し、
不足した規約・対象範囲・重要度の判断だけを補います。
原文を要求するため、注入済みだという申告だけでは完了にしません。

```text
cr: PR #1278のF-03/F-04について、未完了の検証だけを補ってください。
PCR-1のcandidate-only確認です。PR全体を再レビューしないでください。
既存のL1.5担当範囲と権限を守り、実際のcode-quality-reviewerに任せてください。

base: ae6b2dc526263f7f93fcae2a897ad2112b2577d5
head: 47df5af9f0544a78ede6e3b6e7355991293d5d0c
三点差分の実際のmerge-baseも記録してください。

既存の報告として与える事実（この担当のCheckedとは区別します）:
- F-03：通常版TC12の生成元・CSV・Excel E13/L13は「事務局」です。
  画面・画面仕様はbaseから「募集元の担当者」です。
  誤文言は未変更ですが、L13の別の行と画面のTipブロックは変更されています。
  初回Codexは🟢、検証Claudeは🟡としました。
- F-04：通常版TC04のExcel L5だけに「ステータス上昇」が残っています。
  生成元・CSV・画面はbaseから「ステータス増減」です。
  誤文言の手順37は未変更で、同じセルの手順16・35が変更されています。
  両担当とも🟢としました。
- 両者とも既存の不整合です。存在の確認と、このPRでの修正義務は別です。

必ず補う確認:
1. 対象版のcoding-guidelines.md §16、review-prompt.md、CLAUDE.md 5-A/5-Iと、
   適用するgovernance XREV-1/HND-1の原文・適用条件・例外を読んでください。
   ファイル名・引用・grep・注入済みの申告だけで代替しないでください。
   実際の参照パス、版、読んだ完全な節、規約の優先順位を記録してください。
2. projectの差分限定規約と、既存不具合の扱いを照合してください。
   同じセルを変更した事実だけで対象内と決めないでください。
   IN_SCOPEなら、このPRの受入条件か修正義務の根拠を示してください。
3. F-03の🟡/🟢を、具体的な影響と規約から評価してください。
   F-04の誤合格とF-03の誤不合格を比較し、重要度の理由を示してください。
   不一致があるだけで🟡とせず、中央の変更か補足条件かも区別してください。
4. .xlsxの事実を自分の確認済みとする場合は、許可された読取手段でセルを確認します。
   CSV、生成元、変更行数だけでは同じ内容と判定しません。
   禁止されたBash等を追加せず、読めなければ該当判断をUNCONFIRMEDにします。

F-03/F-04ごとに、fact / change_origin / pr_scope / rule_status / severity /
validation recommendation / 原担当のclosure状態を分けてください。
必須規約が未読なら、事実が確定しても総合確認はPARTIALです。
元のApproveや既存判定は変更せず、原担当に返す結論と根拠を示してください。

test-design.mdやTC05などへの追加探索、PR全体の再レビュー、新規指摘の探索、
コード・文書の変更、テスト・CIの実行、他層の起動は禁止です。
既に見つかった周辺事項は範囲外の参考として保持し、必須修正に追加しません。
```

以下は2026-11-12にユーザーが共有したレポートの整理です。
この文書の作成者による独立したコード検証ではありません。

| ID | 発見 | 相互検証の報告 | 残す事項 |
| --- | --- | --- | --- |
| F-01：STGデモの成立表示 | Claude | Codexが事実・変更との関係を確認、🟢 | 原担当による台帳の更新・修正確認は別です |
| F-02：画面概要のTip追記 | Claude | Codexが指定規約の適用を否定 | 検証者の棄却だけで原担当の指摘を閉じません |
| F-03：TC12の相談先 | Codex | Claudeが不一致を確認、🟢から🟡へ評価 | 規約確認不足、PR対象、重要度が未確定です |
| F-04：TC04のExcelラベル | Codex | Claudeが不一致を確認、🟢 | 規約確認不足、PR対象が未確定です |

相互検証には、このほか次の制限がありました。

- 注入済みgovernanceのSHAは申告されましたが、原文との一致は未確認でした。
- 生成元とCSVの変更行数一致は、内容一致の証明に使えません。
- 初回ClaudeはExcelを未確認でした。後の限定検証で読めた範囲だけを更新します。
- 同じセル内の既存誤りと、今回発生した不整合を分けます。
- 規約を読まない理由が「単なる事実確認」でも、必須条件の免除にはなりません。
- 新規担当という記録だけでは、履歴の非継承やバイアス除去を証明できません。

## 4. 検証と導入範囲

`tests/test_parallel_cr_rules.py`は、ルールの必須節、ミラー一致、
入力・出力契約、検証ケースの存在を確認する静的テストです。
実エージェントの遵守や品質を検証するものではありません。
`docs/examples/parallel-cr-cases.json`は、別途許可された実機試験用です。
期待結果は採点側で保持し、新規発見担当に渡しません。

今回の改訂後の並列実行・利用量削減・🟡見逃し改善は未検証です。
既存のモデル、エージェント定義、起動スクリプト、CI、既定ルートは変更しません。
原文と入口が対象環境に展開されたことを確認してから試行します。
この変更自体は、展開やDesktop同期を実行しません。


## 5. Desktop初回試行を踏まえた確認事項

2026-11-12のユーザー共有レポートでは、所要時間は約21分です。
CR-A・CR-B・検証担当の完了が報告されました。
13候補の検証後、手動資料の修正義務と案内の対象範囲が残りました。
この記録はSUPPLIEDです。各担当の実測時間や利用量はありません。

通常25件・詳細152件の各14列を両版で照合したとの報告です。
全件照合が時間を増やした可能性はありますが、内訳は未計測です。
既知のSTGデモ文書の不整合は、最終候補一覧にありませんでした。
未発見か記載漏れかは、担当の全ログを確認していないため未確定です。
この差を、関連文書検索と確認記録の回帰観点として残します。

今回追加した手順は、次のように確認します。

| 確認項目 | 期待する記録 |
| --- | --- |
| 関連文書 | 変更前後の意味・画面ID等からの検索と、運用・デモ手順の判断です。 |
| 生成物 | 選定したケース・セルの実内容と、範囲を広げた理由です。 |
| L1.5の担当範囲 | 局所の不整合と、QA/ADVへの質問を区別します。 |
| 集約 | 重複元のIDを全て残し、既存不具合とPRの修正義務を分けます。 |
| 待機・計測 | list_agentsを使わず、起動・完了イベントと取得可能な利用量を残します。 |
| 判定整理 | 明示許可があるときだけ、原担当へ1回まとめて確認します。 |

関連文書検索は、特定のファイル名を答えとして渡さずに確認します。
既知の指摘や採点用ケースを渡した試験は、新規発見の評価に含めません。
速度や検出率の改善は、新しい実機試行まで未測定です。

### Desktopへの反映

ルールとスキルを更新したため、設定リポジトリをpullした後、
既存の`sync_codex_desktop.py`でdry-run、applyを行います。
手順は`desktop-subagent-sync.md`を参照してください。
通常の`cr:`、モデル、権限、CI、同期スクリプトは変更しません。
同期済みスキルを手編集している場合は、保護を解除して上書きしません。
