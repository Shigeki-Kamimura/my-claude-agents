# 実装中のPCRからPR提出までの手順

実装中にCodex PCRを並行して進めます。
実装差分ができたらClaude Codeのsec-archで独立確認します。
設計リスクがある変更のみ、Claude CodeのADVを追加します。
最終版のPCR・セキュリティ（必要な場合はADV）承認後、次の順に確認します。

1. Claude CodeのQAを行います。
2. Claude CodeのE2Eを行います。
3. Codex標準の `/review` を行います。
4. ユーザーがUXを確認し、承認します。
5. 許可されたPRを提出します。

原文は [pcr-development.md](../.codex/workflows/pcr-development.md) です。
この設定は運用の指示です。自動実行プログラムではありません。
実機での全工程の実行は、まだ確認していません。

## 依頼例

対象の実装チャットで、次のように指定します。

```text
pcr-developmentで、このタスクを進めてください。
実装と並行してCodex PCRを実施してください。
実装差分をClaude Codeのsec-archでも確認し、最終版のSEC_CLEARを得てください。
API契約・認可・DB競合・非同期・互換性のリスクがあればADVを追加してください。
PCR・必要な専門レビューの承認後、Claude CodeのQA、E2Eを行ってください。
次にCodex標準の/reviewを行い、結果と対象範囲を確認してください。
その後、私がUXを確認します。
私のUX承認後に、この変更のドラフトPRを作成してください。
```

この例では、UX承認後のドラフトPR作成も許可します。
同じ許可を毎回求め直す必要はありません。
UX承認そのものは、最終版を確認してから行います。
通常の `cr:` や単独PCRから、全工程は自動開始しません。
設定の更新依頼や、引用された依頼文でも起動しません。

## PCRで確認する範囲

Codex PCRの固定ファイル数上限をなくします。
CR-A・CR-Bは、それぞれ対象差分全体を確認します。
二人でファイルを分け、合計だけで完了とは扱いません。
必要な呼出元・仕様・テスト・文書も確認します。
QA/E2Eのテスト妥当性や、ADVの設計判断は引き取りません。

大きな差分は、読み取りを分割して続けます。
未読箇所、未解決事項、必須規約の不足があれば承認しません。
検証担当は、全指摘と必須確認の不足を検証します。
通常CR、Claude側CR/ADV、QA/E2Eの既存の枠は維持します。

実装途中の版は、差分だけでなく参照先も固定します。
担当が読むソースと、編集中のソースを分けます。
固定できない場合は、レビュー中の編集を止めます。
古い版の承認を、その後の変更へ流用しません。

指摘はまとめて修正し、必要な検証結果を原担当へ渡します。
原担当が差分と影響を確認し、最終版を再承認します。
未完了の初回レビューでは、残りの範囲も確認します。
変更のない規約や証拠は、確認済みの範囲で再利用します。
修正は最大3回です。未解決事項が残れば報告します。

## セキュリティとテストの安全策

PLはチケットからリスクを整理しますが、最終判定は実装差分を見たHQが行います。
すべての実装でClaude Codeの`sec-arch`確認を優先します。呼び出せなければ未確認で止めます。
API契約・認可・DB・非同期・状態管理・互換性に実際のリスクがある場合だけADVも実施します。
`ADV_NOT_APPLICABLE`には、差分に基づく理由を残します。どのレビューも実行したと偽りません。

テストを通すために期待値・モック・スナップショットを弱めたり、テストをスキップ・削除したりしません。
仕様変更によってテストを直す場合は、旧来の保証と新しい期待値、残る検証を記録します。
QA/E2Eは、正常系と異常系のほか、テストが以前の不具合を検出できるかも確認します。
原文：`.claude/knowledge/implementation-security-and-test-integrity.md`。

## 実行権限と標準レビュー

ClaudeのQA/E2Eは、テストの内容と提示された結果を確認します。
レビュー担当は、テスト実行やソース編集を行いません。
テスト、lint、ビルドなどは、許可された実装担当が実行します。
必須検証、専門担当への相談、未解決事項は省略しません。
利用量が不明な場合の確認や、利用制限時の停止も維持します。

`/review` は、標準のコードレビュー機能です。
独自の `/reviewer`、`rev:`、`reviewer` 担当とは区別します。
公式資料は指摘の返却を説明しています。
固定の `Approve` 出力や、承認用の終了コードは確認できません。
出典はOpenAIの [Developer commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
と [Codex CLI](https://learn.chatgpt.com/docs/codex/cli) です。
確認日は2026年11月13日です。

そのため、実際の出力を保ったまま工程の完了を判断します。
全差分の確認完了と、指摘・必須不足の解消が条件です。
運用上の判定名は `STANDARD_REVIEW_CLEAR` とします。
終了コード0や指摘ゼロだけでは、完了にしません。
対象範囲や完了が不明なら、UX承認へ進みません。

## UX承認とPR提出

UX承認は、実際に確認した版とユーザーの回答を記録します。
E2E成功、AIのUX評価、無回答を承認とは扱いません。
画面に影響しない変更は、ユーザーが理由付きで対象外とできます。
ドラフトPRも、通常のPRも、UX承認後に作成します。
早期ドラフトを明示許可した場合は、未通過の工程を記録します。

PR作成の許可がなければ、差分と説明文を用意して確認します。
UX承認だけで、Ready for reviewやマージを許可したとは扱いません。
途中でソース、テスト、要件、規約が変われば再確認します。
PCRと各担当の再承認後、標準レビューとUX承認を取り直します。
提出する内容が、承認した版と一致することも確認します。

## 既存設定との関係

[PR #13](https://github.com/Shigeki-Kamimura/my-claude-agents/pull/13) の
通常CR 10・ADV 12への変更は維持できます。
Codex PCRだけが、その通常枠を引き継がない例外です。
PR #13のマージ前後を問わず、固定上限なしが適用されます。

既存の双方向レビューと、IPR-1は別の運用です。
IPR-1の制御ツールは、この並行実装の実行器には使いません。
QA/E2Eで既存MD経由の呼び出しを明示選択した場合は、
親の手順を記録し、QA/E2Eの後で本手順へ戻します。
旧手順のci-reviewerやドラフトPR作成を自動追加しません。
既存の必須CIや、プロジェクト固有の検証は維持します。

設定は既存のセットアップ、またはDesktop同期で反映します。
この変更自体では、利用中の設定や他プロジェクトを更新しません。
静的テストの成功は、各AIの実行成功を示すものではありません。
