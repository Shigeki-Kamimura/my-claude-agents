# レビュー目的と品質の比較

設定の検査と、実モデルの品質比較を分けます。
反復・独立採点をそろえた実モデル比較は`NOT_RUN`です。
528の単発ADVとNest相談では、原文不足と判定のばらつきを記録しました。
見出しの分割や探索の注意書きだけでは、安定した改善を確認できませんでした。
これらを品質比較の合格や、層追加の効果の証明には数えません。
トークン数、所要時間、指摘数だけで品質維持を判定しません。

## 通常レビューの目的

既存の確認台帳へ、次の対応を短く1回記録します。

`Review objective: 対象操作・責務 → 受入条件・必須規則の出典 → 期待する変更前後 → 担当層・除外`

既存の確認IDを、目的、適用される必須規則、未解決の指摘へ結び付けます。
正常時、意味のある失敗、反証、必要な専門相談も同じ記録にまとめます。
文書や規則だけの変更では、適用条項と例外を確認します。
実行時の不具合を作り出す必要はありません。
受入条件が不明なら、質問と判断への影響を残します。
実装者の説明やテストから、期待する仕様を決めません。

追加調査には、未解決の確認IDと、回答で変わる判断を付けます。
目的を短く書いても、必読資料や必要な周辺経路は省略しません。
関連する既存不具合は、変更前からある事実と範囲判断を残します。
正当なFollow-upを、目的外の誤指摘として数えません。
全未解決ID、独立レビュー、QA/E2E、必須React/Nest相談は維持します。
層の判定とマージ可否は、それぞれの既存契約に従います。

## 比較前に固定するもの

評価担当は、既知の欠陥例、正常例、証拠不足で保留すべき例を用意します。
既知の問題、最も近い反証、期待する判定を、原本参照付きで先に固定します。
例として、変更で生じる表示残り、ガードで防がれる入力、既存不具合を含めます。
規則違反を検出する例と、必須相談が利用できない例も含めます。
各例の対象差分・要件は、その内容を特定できる版で保存します。
React/Nestの例は、対応する実ソースと実相談を使います。
小さな模擬関数だけで、フレームワークの品質を代表させません。

期待値と採点資料はレビュー依頼に含めません。
実装者の結論も渡さず、要件・差分・規則を渡します。
比較する設定版以外は、同じ対象、依頼、モデル、effort、CLI、権限を使います。
例ごとに両条件を最低3回実行し、実行順の偏りも避けます。
3回は記録上の最小条件です。一般的な品質保証や統計的証明ではありません。
設定を変える実験中に、本番案件のレビューや変更を並行して混ぜません。
実行は明示された検証範囲と利用可能な権限で行います。
この手順自体は、モデル起動や追加レビュー層を自動で開始しません。

## 記録と独立採点

[未実行テンプレート](examples/review-quality-assessment.json)を作業用の外部フォルダーへコピーします。
`cases`は事前に確定した評価対象です。テンプレートの例名だけでは実証拠になりません。
各`oracle`には、期待値・コード・要件を根拠付きで固定したファイル参照を指定します。
欠陥例の`expected_defects`は根本原因ごとのIDです。
`required_checks`には、その例で適用される必須確認を漏れなく定義します。
判定保留を試す例では、未了事項の保持と誤承認の防止を評価します。
利用できなかった相談を、実施済みとして採点しません。

各条件の`configuration`は、コミットまたは未コミット設定の内容ハッシュです。
各`runs`の記録は、次の形式です。値は実行記録で置き換えます。

```json
{
  "case_id": "known-regression",
  "repeat": 1,
  "status": "EXECUTED",
  "assessor": "独立評価担当の識別子",
  "assessment_origin": "independent",
  "conditions": {
    "task_snapshot": "対象ソースと要件のSHA-256（64桁）",
    "prompt_sha256": "実際の依頼文のSHA-256（64桁）",
    "role": "adviser",
    "model": "実際のモデル",
    "effort": "実際のeffort",
    "cli_version": "実際のCLI版",
    "tool_policy": "実際の権限制限の版またはハッシュ"
  },
  "evidence": {
    "trace": {"path": "trial-1-trace.jsonl", "sha256": "実ファイルのSHA-256"},
    "output": {"path": "trial-1-output.md", "sha256": "実ファイルのSHA-256"},
    "assessment": {"path": "trial-1-assessment.md", "sha256": "実ファイルのSHA-256"}
  },
  "detected_defects": ["D1"],
  "false_positive_ids": [],
  "scope_error_ids": [],
  "checks": {
    "objective": "COMPLETE", "normal": "COMPLETE", "failure": "COMPLETE",
    "counterevidence": "COMPLETE", "mandatory_rules": "COMPLETE",
    "required_consultations": "COMPLETE"
  },
  "verdict": "REQUEST_CHANGES"
}
```

`EXECUTED`は実際の実行が完了した場合だけです。
評価担当は、期待値、返答、原本、実呼出し記録を照合して採点します。
レビューした本人の自己採点は使いません。
指摘の対応付けは文言一致でなく、到達条件と根本原因で行います。
未採点の項目を空配列や`COMPLETE`で埋めません。
誤指摘と範囲判断の誤りには、返答内の指摘IDを付けます。
必要な相談の起動ID、結果、採否は、採点資料から原本へたどれるようにします。
実行ログは試行ごとに固定します。同じログの複製は追加試行に数えません。
設定側に伝えるのは品質を確かめる方法です。期待する欠陥IDは渡しません。

## 層を追加する候補の比較

追加層は、既存担当と異なる判断を引き受ける場合だけ試します。
各層が同じ範囲を一式調べる候補は採用しません。
既存のCR、L2、QA/E2E、要件未確定時のreq-plを先に使います。
必須相談を任意化したり、既存の層を黙って省いたりしません。
既存の明示的な四層workflowは、順序と最終版の承認条件を維持します。

L2は変更した契約と境界を判断します。
局所コード品質、テスト妥当性、全体の未了管理は各担当へ分けます。
L2の判断が依存する証拠不足は、L2の未了です。
既存の指摘を他担当へ移し、承認を作ることは禁止します。
各担当は必要な原本を独立に確認し、他担当の承認で代用しません。

新しい候補を評価する各runには、次を追加します。

```json
{
  "participants": ["parent", "adviser", "acceptance", "react_l2", "nest_l2"],
  "cost_accounting_reviewed": true,
  "evidence": {
    "trace": {"path": "trial-trace.jsonl", "sha256": "実ファイルのSHA-256"},
    "output": {"path": "trial-output.md", "sha256": "実ファイルのSHA-256"},
    "assessment": {"path": "trial-assessment.md", "sha256": "実ファイルのSHA-256"},
    "usage": {"path": "trial-usage.json", "sha256": "実ファイルのSHA-256"}
  }
}
```

参加者は例です。実際に起動した親・全担当・専門担当を列挙します。
usageは既存のsummarize_codex_session.py等の出力です。
各担当のstatus、tokens、combined_tokens、固定windowを含めます。
評価者は実呼出し記録と照合し、漏れがない場合だけ確認済みにします。
参加者名とusage内の担当一覧は、ツールでも一致を検査します。
実呼出しが全て含まれるかの意味的な確認は、独立評価者が担当します。
同じ使用量ファイルの使い回しは、別試行に数えません。
windowは親の開始から最後の必要な結果までを、同じ基準で採取します。
相談、追加質問、他層への受渡しも含め、保存後の説明は区別します。

```bash
python3 -I -B /absolute/path/to/my-claude-agents/tools/review_quality_report.py \
  /absolute/path/to/assessment.json --out /tmp/review-quality-result.json --require-benefit
```

`benefit.status`は、品質判定と分けて残します。

| 判定 | 意味 |
|---|---|
| `BENEFIT_OBSERVED` | 品質条件を満たし、全例で総tokensが減り、時間の合計・中央値も増えていません |
| `NOT_BENEFICIAL` | 品質条件は満たしますが、総tokensまたは時間の条件を満たしません |
| `INCONCLUSIVE` | 品質比較または全担当の使用量・期間・採点が不足しています |
| `REJECTED` | 品質条件を満たしません。使用量が減っても採用候補にしません |

各例で最低3組を比較します。
tokensは全試行の合計、時間は合計と中央値を使います。
中央値だけで、高額・長時間の外れた試行を隠しません。
`--require-benefit`は、効果未確認なら終了コード4、効果不足なら5です。
品質条件に失敗した場合は、従来どおり終了コード3です。
追加測定を省いた既存の品質比較は使えますが、追加層の採用根拠にはなりません。
常設化は、この限定した比較の結果を確認してから判断します。
実験に成功しても、全案件で同じ効果が出る保証にはしません。

## 集計と判定

```bash
python3 -I -B /absolute/path/to/my-claude-agents/tools/review_quality_report.py \
  /absolute/path/to/assessment.json --out /tmp/review-quality-result.json
```

| 判定 | 意味 | 終了コード |
|---|---|---:|
| `NO_OBSERVED_REGRESSION` | 比較した例で、候補設定が全品質条件を満たしました | 0 |
| 入力エラー | 不正なID、重複試行、入力を上書きする出力先などです | 2 |
| `FAIL` | 見逃し、誤指摘、範囲判断の誤り、必須確認不足、判定不一致があります | 3 |
| `INCONCLUSIVE` | 未実施、未採点、証拠不足、条件不一致、比較回数不足です | 4 |

入力だけでなく、実行ログ・返答・採点・期待値ファイルのハッシュを検査します。
内容の正しさや採点者の独立性そのものは、自動判定しません。
`NO_OBSERVED_REGRESSION`も、比較した例の範囲に限る判定です。
既知欠陥の見逃しが1件でもあれば、他の検出増や消費量削減で相殺しません。
判定失敗と証拠不足が同時にあれば、`FAIL`にして不足事項も残します。
実レビューの承認、CI成功、マージ承認には置き換えません。

未実行テンプレートのまま実行すると`INCONCLUSIVE`、終了コード4になります。
合成データによるツールのテストは、実モデル比較の実行証拠に数えません。
