# Claude Codeレビューの標準方針

2026-11-02採用。特定のPRに限定せず、この方針を使います。
設定の採用と、品質・使用量の改善実証は分けて記録します。
この文書は運用担当向けです。レビュー担当への追加読込は不要です。
実際の指示はCLAUDE.md、担当定義、governanceと配布スキルです。
プロジェクト固有の要件・規則と、実行中のworkflowを優先します。

## 普段の依頼

従来の一行で開始できます。

```text
adv: このブランチをレビューして
```

親は対象リポジトリ、比較元、未コミット範囲、要件を確認します。
PR情報やローカル資料から確定できる項目は自分で埋めます。
比較元など、判断を変える不明点だけを利用者に確認します。
計測値がないことや、依頼書の空欄だけで着手を止めません。
既知の答えや過去の評価資料は、初回発見の入力から外します。
修正確認では、全未解決項目と現在の修正証拠を引き継ぎます。

## 共通の確認手順

1. 要件・規則から、期待する結果を決めます。
2. 利用者や入力、操作、成功・失敗経路、実際の結果をつなぎます。
3. 必要な専門相談を、判定を変える問いに絞ってまとめます。
4. 反証と正常系を確認し、根拠のある範囲だけを判定します。

テストの期待値や実装者の説明だけで、正しい動作を決めません。
遷移先の制限、独立した状態、別の呼出元も必要に応じて追います。
依存先が未変更でも、判断に必要なら確認対象です。
ファイルがあるだけでは、専門相談の対象にはなりません。
既存問題は今回の劣化と分け、受入条件への影響を示します。
新たな仕様を提案する場合は、既存の必須規則と区別します。

## 層ごとの担当範囲

| 指示 | 主に判断すること | 境界 |
|---|---|---|
| cr: | 局所の正しさ、責務、適用規則 | 関数と直接の呼出関係。専門担当を自動追加しません |
| qa: | 単体・結合テストの正常系と失敗系 | 実入力、分岐、assertion、mockで外れた範囲 |
| e2e: | ブラウザー・API境界の流れ | fixtureの利用者、操作、遷移先、観測結果 |
| adv: | 要件と層をまたぐ動作の整合 | 必須React/Nest相談を取得し、回答を統合します |
| rev: | 指定された指摘の収束 | 元の失敗・修正証拠・影響範囲 |

各層が判断に使う証拠は、他層の担当という理由で免除しません。
一方、他層の全体調査は繰り返しません。
追加の層や４層連続レビューは、明示された依頼に従います。
レビュー依頼だけでは、コード変更やテスト実行を始めません。

## 相談と終了条件

専門担当には、判断事項・規則・担当経路・版・不足事実を渡します。
独立した相談は、許可されたツールで並行して進められます。
片方の回答が前提となる相談は、順番に進めます。
実装時の相談を、初回レビューの独立した証拠にはしません。
修正確認は同じ担当へまとめて返します。
逆方向workflowなど、より厳しい継続条件がある場合は従います。

担当の「問題なし」は、確認した条件と経路の範囲に限定します。
未読の必須規則や未取得の必須相談は、未確認として残します。
通常のコードレビューに、CI通過は求めません。
テスト未実行だけでは保留せず、NOT_RUNと注記します。
実行を求めるのは、明示された義務か、静的に解けない具体的なリスクがある場合です。
必要な質問には、対象の義務・リスクと回答による判定の違いを示します。
任意の改善案への未回答は、承認条件にしません。
誤って作った保留項目は、元の担当が理由付きで撤回します。
履歴と正当な残件は維持し、親が判定を書き換えません。
規則違反は重大度の色と分け、解消まで修正要求を維持します。
明示的な例外や規則の変更には、根拠と必要な権限が要ります。
動作を追認するためだけに例外を作りません。
指摘ゼロも有効な結果です。指摘数の目標は設けません。
結果は一つの台帳に統合し、専門担当の全文を重ねて報告しません。

## 使用量と品質の確認

Pro５時間枠の約30ポイントを、１依頼全体の目標とします。
親・専門担当・補足確認を含みます。使い切る目標ではありません。
未完了なら、残件と担当を残してPARTIAL/DEFER等で報告します。
使用率が取れない場合はNOT_MEASUREDです。
トークン数やキャッシュ量から、使用率を推定しません。
計測方法は [試行記録](claude-review-trial.md) にまとめます。

今後の別PRでは、適用設定と同じ対象版を固定して評価します。
比較用の期待結果は、初回担当へ渡す前に別記録へ固定します。
UI、API・権限、データ・非同期など、異なる経路で確認します。
それぞれ既知不具合、正常な例外、証拠不足の事例を含めます。
不要な追加レビューを自動実行する指示ではありません。

採点は、見落とし、誤検出、必須確認、判定根拠、時間・使用量です。
候補提示後の発見は、初回の発見成績と分けます。
静的な設定検査が通っても、実レビューの品質向上とは言えません。
現在、30ポイント達成と他PRでの品質維持は未実証です。
528の繰り返しだけで調整を続けず、通常運用の別PRで検証します。
